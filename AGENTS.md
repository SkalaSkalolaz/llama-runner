# AGENTS.md

Общие инструкции для Claude Code во всех проектах. Проектный CLAUDE.md /
AGENTS.md может дополнять или переопределять их — при конфликте побеждает
проектный файл.

Основной язык — Go. Другие языки встречаются редко: в них действуют те же
принципы, но конкретные команды и конвенции берутся из README/CI проекта
(см. «Проверка перед сдачей»).

## Определение стека

Перед первой правкой в незнакомом проекте определи стек по маркерам в корне:

    go.mod → Go;

    package.json → Node/TypeScript;

    Cargo.toml → Rust;

    pyproject.toml / requirements.txt → Python;

    pom.xml / build.gradle → Java/Kotlin;

    иначе — прочитай README и CI-конфиг.

Если стек неочевиден или в проекте несколько стеков — спроси, а не угадывай.

## Правила написания кода

    Одна связная ответственность на модуль. Это главный принцип; он важнее
    любых числовых лимитов.

    Размер файла — ориентир 300–500 строк. Если файл стабильно превышает
    верхнюю границу, декомпозируй по функциональному назначению. Не жертвуй
    логической связностью или читаемостью ради числа: лучше осознанно оставить
    файл на 600 строк, чем разрезать по живому.

    Разделяй по назначению, а не по количеству. Два файла по 400 строк с
    разными обязанностями лучше одного на 800 со смешанными.

    Вноси изменения небольшими, логически завершёнными шагами. Один шаг —
    одна причина; не смешивай рефакторинг и новую функциональность.

    Не меняй публичные API без необходимости. Если сигнатура функции,
    экспортируемый идентификатор или формат файла меняются — отметь это явно.

    Следуй стилю окружающего кода. Не переформатируй чужие файлы «под себя»;
    для нового кода — конвенции проекта (для Go — gofmt).

## Go: специфика

    Форматирование — только gofmt (не ручное выравнивание).

    Именование — по Effective Go и Go Code Review Comments: короткие имена в
    узких скоупах, MixedCaps, никаких GetFoo для геттеров.

    Ошибки — возвращать, не паниковать; оборачивать через %w; проверять через
    errors.Is/errors.As, не сравнением строк.

    Контекст — первым аргументом, context.Background() только на верхнем уровне.

    Горутины — с явным завершением (канал, context, defer); не оставляй
    «висящих» горутин.

    Пакеты — маленькие, по одной ответственности; internal/ для того, что не
    должно быть публичным API.

    Зависимости — не добавляй новые без явной необходимости; если добавляешь —
    объясни, почему стандартная библиотека не подходит.

    Не отключай линтер и не добавляй //nolint без объяснения причины.

## Другие языки

    Конвенции — из README, линтера и CI проекта. Если их нет — стандарт языка
    (PEP 8 для Python, Prettier/ESLint для JS/TS, rustfmt для Rust и т.д.).

    Не смешивай стили в одном файле: если файл уже написан в одном стиле —
    продолжай в нём.

    Не добавляй # noqa, @ts-ignore, eslint-disable без объяснения.

## Поиск внешней информации

Когда локальных знаний не хватает, ищи в интернете — но сначала проверь,
что этого нет локально, и всегда фиксируй версию, под которую ищешь.

Когда искать: ошибка undefined: X / no such method / cannot use Y as Z;
deprecated: в предупреждениях; незнакомое сообщение об ошибке; breaking changes
при обновлении зависимости; CVE/security advisory; неочевидное поведение
stdlib/фреймворка; спецификации протоколов и форматов.

### Сначала локально (не искать в интернете, если ответ нашёлся):

    go doc <pkg> и go doc <pkg>.<Symbol> — дока установленной версии.

    grep по vendor/ (если есть) и по самому репозиторию.

    README, docs/, CHANGELOG.md, CONTRIBUTING.md.

    go list -m -versions <module> — какие версии существуют.

    git log / git blame по зависимости, если она vendored или форкнута.

    Существующие тесты и golden-файлы — они фиксируют фактическое поведение.

Порядок источников: официальная дока нужной версии (pkg.go.dev/<pkg>@<version>)
→ changelog / release notes → GitHub issues по точному тексту ошибки →
security advisories (pkg.go.dev/vuln, osv.dev, govulncheck) → Stack Overflow
и блоги (только если предыдущее не дало ответа; помечай как менее надёжные).

### Правила поиска:

    Сначала версия, потом поиск. Прочитай go.mod (или package.json,
    Cargo.toml, pyproject.toml), зафиксируй версию, ищи под неё. Не цитируй
    документацию master-ветки, если у тебя v1.2.3.

    Цитируй URL. Не выдумывай ссылки: если URL не открывается — его нет.

    Проверяй дату. Статья 2019 года про API, менявшийся трижды, может навредить.

    Сверяй с кодом. Для breaking changes недостаточно changelog: проверь
    сигнатуры через go doc, прогони тесты, убедись, что компилируется.

    Противоречие «дока vs код» — доверяй коду и тестам проекта, но отметь
    расхождение в ответе.

    Не отправляй в поиск секреты и приватный код. Запрос формулируй
    обобщённо: текст ошибки, имя API, версия пакета. Токены, ключи, имена
    внутренних сервисов, фрагменты проприетарного кода — никогда в запрос.

Инструменты: mcp-search-server (если запущен через llama-runner);
встроенный WebSearch/WebFetch Claude Code; curl — только для прямых
запросов к официальным источникам (pkg.go.dev, proxy.golang.org,
raw.githubusercontent.com), не для поиска; govulncheck ./... — для CVE.

Если интернета нет или поиск недоступен: скажи об этом явно; предложи
альтернативу (go doc, локальные доки, vendor/, вопрос пользователю); не
выдумывай API по памяти — лучше спросить.

После того как нашёл: кратко резюмируй (что, где, какая версия, что это
меняет в коде). Если нужно обновить зависимость — не обновляй молча: предложи,
покажи diff go.mod/go.sum (или эквивалент), дождись подтверждения. Если
нашёл CVE — сообщи явно, даже если не спрашивали.

## Тесты

    Все новые и изменённые функции покрываются unit-тестами. Для
    существующих — не хуже текущего покрытия.

    Тесты — часть изменения, а не отдельная задача. При добавлении
    функциональности, изменении поведения или исправлении бага добавляй тесты
    в той же правке.

    Не ослабляй и не удаляй тесты ради зелёного прогона. Упал тест — чини
    причину. Устарел — обнови осознанно и объясни, почему.

    Не трогай golden-файлы (testdata/** и аналоги) без явного указания.
    Для регенерации используй штатный флаг (-update или аналог) и показывай diff.

## Проверка перед сдачей

Перед тем как сказать «готово», прогони проверки для стека проекта и покажи
результат.

### Go (по умолчанию):

    gofmt -l . — пусто;

    go build ./... — без ошибок;

    go vet ./... — без предупреждений;

    go test -race -cover ./... — все пакеты ok.

Другие языки: команды бери из README или CI проекта (.github/workflows/*,
Makefile, package.json scripts, pyproject.toml). Если их нет — стандарт
языка (pytest, npm test, cargo test и т.п.). В ответе явно перечисли,
какие проверки прогнал.

Общее: если проверка неприменима (нет Go, нет тестов, нет линтера) — скажи
об этом явно, не молчи. Не отключай линтер и не добавляй подавления
(//nolint, # noqa, @ts-ignore) без объяснения.

## Что не трогать / Безопасность

    Не коммить изменения без прямой просьбы пользователя.

    Никогда не коммить .env, *.key, *.pem, credentials, токены и
    любые другие секреты. Если секрет случайно попал в diff — остановись и сообщи.

    Не меняй lock-файлы зависимостей без явного указания: go.mod/go.sum
    (Go), package-lock.json/pnpm-lock.yaml (Node), Cargo.lock (Rust),
    poetry.lock/requirements.txt (Python) и т.п. Обновление зависимостей —
    отдельная задача.

    Не трогай .github/workflows/**, Dockerfile, Makefile, Justfile
    и прочие инфраструктурные файлы без явного указания.

    Не выполняй команды, изменяющие систему за пределами рабочей директории
    проекта: sudo, глобальные установки, правка ~/.config, ~/.ssh и т.п.

    Не запускай долгие команды без предупреждения (сборка всего проекта,
    полный прогон тестов с -race на большом репозитории) — сначала скажи,
    сколько это может занять.

## Коммиты

    Никогда не коммить изменения без прямой просьбы пользователя.

    Если просьба есть — коммить только то, что относится к задаче; не подмешивай
    посторонние правки.

    Сообщение — Conventional Commits: type(scope): subject. Тело — что и
    почему; футер — ссылки на issue, если есть.

    Не делай git push, --amend, --force, rebase без явной просьбы.

## Главное правило
